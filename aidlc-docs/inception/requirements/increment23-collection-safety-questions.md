## 2. Grounding facts (verified in code, 2026-08-05)

### The five vectors, as they stand today

- **V1 — `resetPool()`**: `src/features/pool/writer.ts:81-85` runs `db.delete(collections)` →
  `db.delete(cards)` → `db.delete(themes)`. Called from `scripts/seed/index.ts:71-73` when
  `--publish --reset` is present. **No confirmation, no dry-run, no environment check.**
  `pnpm seed` = `tsx --env-file-if-exists=.env.local` `[package.json:20]`, and `.env.local` holds the
  **production** Neon URL (verified: host `ep-wandering-sky-…-pooler.c-9.us-east-1.aws.neon.tech`).
  Confirmed exactly as the vision describes.
- **V2 — `--sync` prune**: `scripts/seed/index.ts:149-165` calls `deleteCardsNotIn` per theme and
  `deleteThemesNotIn` once, both routed through `pruneNotIn` `[writer.ts:14-23]`. `collections.card_id`
  and `collections.child_id` are both `onDelete: cascade` `[src/db/schema.ts:81,84]`, so a renamed
  theme in `seed/cards.json` silently destroys every child's cards in it. Confirmed.
- **V3 — profile delete**: `RemoveProfileButton.tsx:27` is a bare `window.confirm`, submitting to
  `removeProfileAction` → `profileService.removeChild` → `pgProfileStore.remove` →
  `db.delete(children)` `[profile-store.pg.ts:38]`, cascading to `collections`, `quiz_completions`
  and `collection_rewards`. Confirmed.
- **V4 — destructive migrations**: 7 migrations `0000`–`0006` applied to prod. Nothing mechanical
  prevents an eighth from dropping data.
- **V5 — no backup**: confirmed. **`.github/` does not exist** in this repository at all.

**Complete inventory of `collections`-deleting code** (grep, whole repo, excluding migrations):
`writer.ts:21` (`pruneNotIn`, via cascade), `writer.ts:82` (direct), `profile-store.pg.ts:38`
(via cascade). Three sites. This matters for Q2.

### ⚠️ Finding that contradicts the feature's Technical Environment

`Product-Definition/features/collection-safety/technical-environment.md` states *"Private repo
`nywleswoey/kids-collection` `[from: gh repo view]`"* and makes it a security property:
*"Artifacts contain a full copy of the production database. Repository visibility is what protects
them; the repo must stay private."*

**`gh repo view` today returns `"visibility":"PUBLIC","isPrivate":false`.**
(`nywleswoey/kids-collection`, created 2026-07-11, pushed 2026-08-04.)

What follows from that:

- **Workflow artifacts inherit repository read access**, so on a public repo the nightly dump is
  downloadable by anyone, as are the run logs.
- The stated Actions budget changes in the *user's favour* — public repos get unlimited standard-runner
  minutes, so the "2,000 min/month, ~45 min used" arithmetic is moot.
- The `DATABASE_URL` secret itself is not exposed by artifact visibility (secrets are not passed to fork
  PRs), but a `pg_dump` failure can print a connection string into a world-readable log.

**Resolved at Q1 = D**: the repo stays public and the dump is stored unencrypted, because the owner
classifies the collection data as non-sensitive. The feature's technical-environment.md security
paragraph and its Actions-budget line are both superseded by that decision — see Q1 for the exact
write-backs. What survives the reclassification is the credential boundary: the `DATABASE_URL` must
never reach a public log.

### Backup mechanics — facts the design will hit

- The production `DATABASE_URL` points at the **`-pooler`** endpoint. `pg_dump` against a
  transaction-pooling endpoint is not reliable (it needs session-level state and a consistent
  snapshot). The dump should use the **direct** (non-pooler) host. See **Q13**.
- `pnpm pg:up` `[package.json:15]` starts `postgres:16-alpine` on port 5499 via
  `tests-pg/docker-compose.yml` **and then applies every migration in order**. The restore drill needs
  an **empty** database — a `pg_restore` of a full dump recreates the schema itself, so re-using
  `pg:up` verbatim would collide. Re-use the compose file's `pg` service; skip the migration loop.
- `tests-pg/docker-compose.yml` also defines a `neon-proxy` service the drill does not need.
- Scheduled workflows are **disabled automatically after 60 days of repository inactivity** (GitHub
  behaviour, owner is emailed). Relevant to "fully automated, zero touch" — see **Q16**.

### V3 confirmation — what data exists today

`app/admin/profiles/page.tsx` renders from `profileService.listChildren()`, which returns only
name / avatar / `pullTokens` / `easterEggTickets` — **there is no card count on that page today**.
Options that need *no new port method* (the technical environment forbids one here):
`CollectionStore.ownedCardIds(childId).size` (existing port method → distinct cards owned), or
`binderService.getBinder(childId).totalOwned` (existing service → same number, heavier read).
**Total copies including duplicates has no existing read** and would require one. See **Q11**.

## Questions

### Q1 — RESOLVED: the repository is PUBLIC, and artifacts inherit repo read access
The feature's technical environment assumes a private repo and rests the artifact's confidentiality on
that. It is not true today, so the assumption had to be replaced with a decision.

A) **Flip `nywleswoey/kids-collection` to private before the workflow ships.** Restores the documented
   security property exactly as designed; nothing else in the design changes. (Recommended)
B) Keep the repo public and **encrypt the dump before upload** (`gpg --symmetric`, passphrase held as
   a second Actions secret + in your password manager). Still $0. Adds one secret whose loss makes
   every backup unrecoverable, and the restore runbook gains a decryption step.
C) A + B together — private repo **and** an encrypted artifact (defence in depth).
D) Keep the repo public and accept publishing a full copy of the database nightly.

[Answer]: **D — the repository stays public and the dump artifact is stored unencrypted.**
Owner's decision, stated directly: *"the data is not sensitive and therefore i don't need to encrypt
the backup nor enforce the repo to be private."* The data classification is the owner's to make — they
are the operator, the data controller and the children's guardian.

**Consequences of D, now load-bearing:**
- **Backup content is public by design.** The artifact contains the three children's display names,
  their collection history, ticket balances and quiz records. This is an accepted classification, not
  an oversight — it must be recorded that way so a future reader does not "fix" it as a bug.
- **The `DATABASE_URL` secret is emphatically NOT covered by that classification.** The dump is public;
  a write-capable connection string is not. The workflow must never echo it, and `pg_dump` stderr must
  be suppressed or redacted (a failure can print the connection string into a public log). Q14's
  read-only role becomes more valuable, not less.
- **Public logs, too.** Actions run logs on a public repo are world-readable. The blast-radius output,
  row counts and table names are fine under this classification; credentials are not.
- Public repos get **unlimited** standard-runner minutes — the "2,000 min/month, ~45 min used"
  arithmetic in the feature's technical environment is moot, and future CI (parent OQ-T-2) draws from
  no shared pool.
- Secrets are not passed to fork pull requests and `workflow_dispatch` requires write access, so a
  schedule-only workflow has no untrusted-code path to the secret.
- **Two delta write-backs** (recorded in the requirements document, not silently applied):
  1. Feature `technical-environment.md` §Security — *"Artifacts contain a full copy of the production
     database. Repository visibility is what protects them; the repo must stay private, and that is now
     a security property, not merely a preference"* is **superseded**. Replacement: the repo is public,
     the collection data is classified non-sensitive, and the only confidentiality boundary in this
     feature is the `DATABASE_URL` secret.
  2. Feature `technical-environment.md` §Cloud Services — "Private repo … 2,000 minutes/month included"
     is factually wrong; public repos get unlimited standard-runner minutes.
- **This does not touch any parent boundary.** The parent's kid-safety rule governs *what reaches a
  child*, not what leaves the database; the auth allowlist, admin gate, HMAC offers and
  "no secret in the client bundle" are all unaffected. Worth stating explicitly because the parent
  document's compliance section notes its reasoning holds *"because the app is private"* — that concerns
  public **sign-up**, not repository visibility, and is unchanged.

### Q2 — OQ-CS-3: the general delete-path property test

`collections`-deleting sites in the whole repo, which makes a mechanical alternative cheap.

B) Narrow test **plus a source-level guard test**: assert that `collections` is deleted (directly or
   by cascade-capable prune) from exactly the three known sites, so a fourth path fails CI the day it
   is written. Cheap, mechanical, and closes the "declared but not enforced" shape. (Recommended)

[Answer]: A — **OQ-CS-3 stays OPEN**, scheduled after slice 1. Slice 1 ships the narrow `resetPool()`
test only. The parent's blocking-PBT constraint remains unmet for the general delete path, and that
tension is carried forward deliberately rather than closed.
