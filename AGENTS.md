# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- New card themes follow `seed-content/NEW-THEME-RUNBOOK.md`. Lanes are the registry in `src/shared/pool/providers/index.ts`; no escape hatch is currently registered (ai-horde, the first one, was retired). `supergrok-manual` is an opt-in drop folder (`pnpm seed --supergrok-export`); there is no xAI API key.
- `scripts/seed/index.ts`'s CLI flags are parsed by `scripts/seed/args.ts` (`parseSeedArgs`, strict `node:util parseArgs`). Add a new flag or command there, not via `process.argv.includes` in `main()`/`runSeed()`. Any code that deletes pool rows by a keep-list (prune previews or the real pruners) should share `notKept()` in `src/shared/pool/prune-predicate.ts` rather than re-implementing the empty-keep-list rule. The only commands are `--review` and `--sync` (plus the standalone read-only/export ones) — `--publish`, `--reset` and `--allow-unreviewed` were removed as dead/unsafe; `resetPool`/`previewReset` survive only for `tests-pg` to call directly.
- Prototype scripts live in `archive/prototypes/` (not `scripts/prototypes/`) once retired — run them with `tsx`, not a `pnpm prototype:*` script, which no longer exists.
- Passkey cutover is done: `docs/PASSKEY-CUTOVER.md`'s deploy 2 is cancelled and `ADMIN_PASSCODE` stays (see the decision note at the top of that doc).
- `scripts/backup/*.ts` must stay dependency-free (only `node:fs`/`node:crypto`/`node:path`/`node:url`): `backup.yml` runs them with plain `node` (Node 24's built-in type stripping), not `tsx`, so the nightly job needs no `pnpm install` next to `secrets.BACKUP_DATABASE_URL`. A relative import between them needs an explicit `.ts` extension (`tsconfig.json`'s `allowImportingTsExtensions`) because Node's ESM resolver, unlike `tsx`, requires one. `backup.yml` also gates on `drizzle.__drizzle_migrations` vs. `src/db/migrations/meta/_journal.json` (`scripts/backup/check-migrations.ts`) — see CONTRIBUTING.md's Migrations section.
- `tests-pg/db.ts`'s `resetAll()` derives its `TRUNCATE` table list from `src/db/schema.ts` via `drizzle-orm`'s `isTable`/`getTableName` — a new table needs no edit there.
- Postgres access uses the neon-http driver, which has **no interactive transactions** (`db.transaction` throws at runtime). Any write that must be atomic across multiple statements/tables goes through ONE chained-CTE `db.execute(sql\`...\`)` statement instead — see `collection-store.pg.ts`'s `swapCards` and `claim-store.pg.ts`. `pull()`'s request-level idempotency (`src/features/pull/pull-service.ts`, `src/db/stores/claim-store.*`) is built this way: a `pull_claims` row with a fence-guarded "granting"/"done" lease, so a killed/retried pull can never double-spend or double-grant. Don't reorder `pull()`'s deduct-then-draw steps without re-reading that file's doc comments first. `pull()` accepts an optional `prefetch` (already-started catalog/owned-ids reads); `pullAction` is the only caller that passes one, started against the active-child cookie's *raw, unvalidated* id concurrently with the gate check itself (`peekActiveChildId` in `active-profile.ts`, `prefetchPullReads` in `pull-service.prod.ts`) rather than after it — safe because `pull()` only ever runs once the gate has confirmed that same id. Within ONE chained-CTE statement, a table can be WRITTEN at most once — a later CTE's UPDATE gated on `EXISTS(earlier_insert_cte)` into the SAME table matches zero rows even though that insert just committed (confirmed directly against local Postgres), because a sibling CTE can't see another's write to the same table within one statement. A claim/grant that needs two writes to its own claims table (insert-to-reserve, then update-to-finish) therefore needs TWO statements/round-trips, like `claim-store.pg.ts`'s `claimAndSpend` + `finishWithCardGrant` split — `offer-claim-store.pg.ts`'s `claimOffer` (the single-use easter-egg offer redemption, keyed by a signed `jti`, same two-phase shape) is the second example.
- Any `revalidatePath` call in a server action (for any route) re-renders the *current* route into the action's own response — see the comment on `pullAction` in `src/features/pull/actions.ts`. So if a server component's JSX conditionally mounts a client child on a value the action just changed, React unmounts that child and drops its local post-action state (a success message, etc.) the instant the response lands. Gate the child's visibility on that prop *inside* the client component instead; see `SacrificePanel.tsx`.
- **The `tests-pg/docker-compose.yml` Postgres binds FIXED host ports (5499/4499) as a single Docker Compose project (`kc-pgtest`), so it is shared by every concurrent treehouse worktree/session of this project on the machine, not per-worktree.** A sibling lane's `resetAll()` (TRUNCATE) can race with your rows, `pnpm pg:down`/`pg:up` mid-test can wipe uncommitted migrations or drop the container entirely underneath a concurrent `pnpm test:pg` run, and `local-neon-http-proxy` has a hard-capped connection pool (20) that degrades hard (every query "throws away" a connection) under sustained concurrent load from several sessions. Never run `pnpm pg:down` and avoid redundant `pnpm pg:up` unless you've confirmed it's actually down — coordinate first if you suspect other sessions are using it. Before trusting an isolated, non-reproducing `test:pg` failure (FK violations, ECONNREFUSED, count mismatches) as a real regression, rule out a concurrent sibling touching the same container; re-running the same file alone is the fastest way to tell the two apart.
