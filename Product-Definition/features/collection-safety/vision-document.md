## Executive Summary

**Collection Safety** closes the single largest unmitigated risk in Star Catchers: the children's
collections — every pull the three kids have ever made — can currently be destroyed by one mistyped
command, and there is no backup to restore them from. The parent definition already names this as the
hard boundary above all others (*"The children's existing collection data — above all else"*) and tracks
it as **OQ-B-1**, the only open question *"where the downside is irreversible data loss."*

A pre-interview scan of the repository found **five deletion vectors**, two of which require no mistake
more serious than a typo and are guarded by nothing at all. This feature blocks the worst of them,
adds friction to the rest, and puts a verified, automated backup underneath everything.

The approach is **prevention first, recovery as the safety net**. It is deliberately small: six items,
all buildable in hours, at **$0/month** and with zero ongoing upkeep.

## Business Context

### Problem Statement

The parent's own stated hard boundary is that the children's collection rows can never be lost. Nothing
in the system enforces that. The gap between the policy and the mechanism is total:

- `pnpm seed --publish --reset` calls `resetPool()`, which runs `db.delete(collections)` against every
  row, for every child, with **no confirmation, no dry-run and no environment check**
  `[from: src/features/pool/writer.ts:81-85]`. `pnpm seed` loads `.env.local`, which holds the
  **production** `DATABASE_URL`. One flag, typed once, is irreversible.
- `pnpm seed --sync` prunes any theme or card missing from `seed/cards.json`, and the schema's
  `onDelete: cascade` `[from: src/db/schema.ts:81-84]` carries that delete straight into `collections`.
  Renaming a theme in a JSON file silently destroys every child's cards in it.
- If either happens — or the Neon project is lost — **there is no backup**. No `pg_dump`, no backup
  script, no restore runbook exists in the repository.

The emotional stakes are what make this worth a feature rather than a note. A lost collection is not a
data-integrity incident; it is telling a 4-, 7- and 9-year-old that the thing they have been building
for a month is gone, with no way to get it back.

### Business Drivers

No external driver and no deadline — the same personal-project context as the parent definition. The
"why now" is that the exposure has been live and unguarded for 22 increments, and the user raised it
directly: *"i need to ensure that my kids' collections are not deleted by mistake."*

### Target Users and Stakeholders

| Role | Description | Primary Need |
|------|-------------|--------------|
| Parent (operator) | The only person who can trigger any of the five vectors — and the only person who can recover from them. Sole developer, sole operator, no second reviewer. | To be unable to destroy the collections by accident, and to be able to restore them if it happens anyway — without ongoing effort or cost. |
| The three children (4, 7, 9) | Never see this feature. Affected only by its absence. | Their collections keep existing. |

The children are stakeholders with no interface: **success here is invisible to them by definition.**

### Business Constraints

- **Strictly $0/month.** Free tier only. Inherited from the parent definition's single success metric and
  reaffirmed explicitly in this interview (Q7).
- **Fully automated, zero touch.** A backup requiring a remembered manual step is one that stops
  happening — and the failure mode this protects against is precisely "wasn't paying attention".
- **One-person team.** Nothing that adds an operational surface to monitor.
- **Full-database dump, no table allowlist** (Q1, amended). An enumerated table list is itself a way to
  lose data by mistake: a table added by a future migration would silently fall outside the backup.

### Success Metrics

| Metric | Current State | Target State | Measurement Method |
|--------|---------------|--------------|--------------------|
| Collection rows lost to an operator action | Unprotected — no mechanism prevents or recovers a total wipe | Zero, and provably recoverable | An automated restore drill that restores the dump into a throwaway Postgres and asserts row counts (T5) |
| Paths to bulk deletion without an explicit, named, confirmed action | 2 wide open (V1, V2); 1 weakly guarded (V3) | Zero | Structural — the guards are code, testable by a test suite |

Both are required together (Q4 = A + C). The second is mechanically verifiable today; the first proves
the safety net actually works rather than merely existing. **An untested backup is a belief, not a backup.**

## Full Scope Vision

### Product Vision Statement

> The collections cannot be destroyed by a moment's inattention — and if they somehow are, they come back.

### Feature Areas

**1. Structural prevention (V1)** — `resetPool()` is split so that resetting the card pool never touches
`collections`. Wiping children's rows becomes a separate, explicitly-named operation rather than a side
effect of a routine seeding command.

**2. Destructive-command guards (V1, V2)** — seed scripts detect a production `DATABASE_URL`, print the
blast radius in rows, and require both a fresh CLI argument and a typed confirmation. Covers `--sync`
prunes as well as `--reset`; V2 is the more dangerous of the two precisely because nothing about it
sounds destructive.

**3. Deliberate profile deletion (V3)** — the `window.confirm` becomes a type-the-name confirmation
showing the card count about to be destroyed.

**4. Automated backup (V5)** — a nightly full `pg_dump` via GitHub Actions, retained 90 days, plus a
manual trigger so a dump can be taken immediately before running anything destructive.

**5. Verified recovery (V5)** — the workflow restores its own dump into a throwaway Postgres and asserts
row counts, so a silently-corrupt backup fails loudly instead of at the worst possible moment.

**6. Platform recovery, documented (OQ-B-1)** — Neon PITR verified at a **6-hour** retention window, with
what it does and does not cover written down.

### Recovery Coverage — the resulting picture

| Time since the mistake | Covered by | Loss |
|---|---|---|
| 0–6 h | Neon PITR — restore to the exact second before | ~none |
| 6–24 h | Last nightly dump | up to 24 h of pulls |
| > 24 h, up to 90 days | Older nightly dumps | up to 24 h of pulls, from that day |
| > 90 days | **Nothing** | total |

The **6–24 h band has no point-in-time capability**: recovery means restoring last night's dump and
accepting that day's pulls are gone. That matches the chosen RPO — recorded here so it is a known
property rather than a discovery made mid-incident.

### Future Extensions (not committed)

- **Soft-delete / archive for child profiles** — the *decided target design* (Q3 = b), deferred out of the
  first slice. Turns the worst single-click accident in the app into an undo, at the cost of one nullable
  `archived_at` column. Tracked as **OQ-CS-2**.
- **General delete-path property test** — "no service path can delete a `collections` row it doesn't own",
  covering V4 broadly rather than the one function T7 pins down. Tracked as **OQ-CS-3**.

## MVP Scope — Features IN

| Feature | Rationale | Vector |
|---------|-----------|--------|
| Split `resetPool()` so pool reset never deletes `collections` | Removes the loaded gun rather than adding a safety catch. The only item that makes a total wipe *structurally impossible* rather than merely harder | V1 |
| `--sync` prune guard: print what will be destroyed, require an explicit flag | The silent vector. A typo in a JSON file currently destroys real cards with no signal at all | V2 |
| Type-the-name profile-delete confirmation showing card count | `window.confirm` is one misclick; typing a name is a deliberate act | V3 |
| Production-DB guard on destructive scripts (host detection + typed confirmation) | The whole V1 scenario is "`.env.local` was loaded and I didn't think about it" | V1, V2 |
| Nightly full `pg_dump` via GitHub Actions + documented restore runbook | The only thing that covers a mistake nobody notices in time | V5 |
| Verify Neon PITR and document coverage | Closes parent **OQ-B-1**; covers the fast-noticed case far better than a nightly dump | V5 |

### Non-Functional Priorities

- **Cost**: strictly $0/month, free tier only — non-negotiable, inherited from the parent's single metric.
- **Upkeep**: zero touch. Fully automated or it doesn't count.
- **Verifiability**: every guard must be testable, and the backup must prove itself on every run.
- **Explicitly not priorities**: latency, scale, availability of the backup job. A backup that runs late
  is fine; one that runs silently wrong is not.

## What Must NOT Change

⚠️ Additions to the parent definition's hard boundary. Each is a constraint on all future work.

- **A pool reset must never delete `collections` rows.** Resetting the card pool and destroying the
  children's cards are different operations and must stay different operations. This is the invariant the
  whole feature exists to establish — re-merging them for convenience re-arms V1 exactly as it was.
- **Destructive seed operations must detect production and require a fresh, typed confirmation.** Not an
  environment variable — the failure mode being guarded against is a stale flag in the very file that
  supplies the production credential.
- **The backup must be a full dump.** No `-t` table allowlist, ever. A future migration's new table must
  be backed up without anyone remembering to add it.
- **The restore drill runs on every backup run.** A backup that is not verified is not a backup, and the
  moment the drill becomes optional is the moment it stops being true.
