## Project Technical Summary

- **Scope**: accidental-deletion protection for the children's collections — prevention guards in the
  existing seed scripts and admin UI, plus an automated, verified backup.
- **New runtime surface**: **one** — a GitHub Actions scheduled workflow. Nothing is added to the deployed
  application; no new code runs in the request path.
- **Team**: one person, no second reviewer, no on-call. The parent document's governing rule applies with
  full force here: *prefer boring, low-maintenance, zero-ceremony choices.*
- **Cost envelope**: strictly $0/month, free tier only.

## Frameworks and Libraries

### Required — new

| Tool | Domain | Rationale |
|------|--------|-----------|
| `pg_dump` / `pg_restore` (postgresql-client ≥ 16) | Backup and restore | The full-dump requirement (Q1) rules out anything that enumerates tables. Standard, boring, and already the format any future recovery would expect |
| GitHub Actions | Scheduled execution | The only free, genuinely unattended runner available here that can execute a real `pg_dump` |

### Rejected during this interview

| Rejected | Reason |
|----------|--------|
| **Vercel Cron → Function** | Vercel Functions have no `pg_dump` binary. A hand-rolled dump would query table by table, reintroducing the exact "keep a table list in sync" failure mode Q1 rejected. Vercel Hobby cron is also once-daily and best-effort |
| **Local machine cron / launchd** | Free, but fails "fully automated, zero touch" — it only runs when the laptop is awake |
| **Neon PITR as the only layer** | Verified at a **6-hour** window. Excellent for the fast-noticed case, useless for anything older. Necessary, not sufficient |
| **Any managed backup service** | Parent deny-list: no metered or paid third-party services |

### Prohibited Patterns — additions

Ways an agent could plausibly break this feature *while writing reasonable-looking code*:

- **Don't add `-t` / `--table` to the `pg_dump` invocation.** The full dump is the mechanism, not a default.
  Narrowing it re-creates OQ-CS-1 silently — a table added by a future migration would simply stop being
  backed up, and nobody would find out until a restore.
- **Don't make `resetPool()` "convenient" again.** Deleting `collections` inside a pool reset is the
  original defect (V1). If a caller genuinely needs both, it calls both, explicitly.
- **Don't move the destructive guard into an environment variable.** The scenario being defended against
  is a stale value in `.env.local` — the same file that supplies the production credential. The guard must
  require input that cannot be pre-set.
- **Don't skip the restore assertion to make the workflow faster.** An unverified backup is the failure
  mode this feature exists to prevent, not an acceptable optimisation.
- **Don't let the guard cover only `--reset`.** V2 (`--sync` prune) destroys data with no
  destructive-sounding flag at all, which is what makes it the more dangerous vector.

## Architecture and Patterns

### Where the guards live

The parent's persistence seam governs this. The guards belong at two distinct altitudes, and conflating
them is the likeliest design error:

- **Script-level (V1, V2)** — production detection, blast-radius reporting, typed confirmation. These are
  operator-interaction concerns and belong in `scripts/seed/`, **not** in `src/features/pool/writer.ts`.
  A port method must never prompt.
- **Function-level (V1)** — the `resetPool()` split is a change to what the function *does*. It stays in
  the writer module and is pinned by a test.
- **UI-level (V3)** — the type-the-name confirmation is a client component concern
  (`RemoveProfileButton.tsx`), with no change to `removeProfileAction` or the `ProfileStore` port.

**Constraint**: no new port method is needed for any of this. If the build reaches for one, that is a
signal the guard has been placed at the wrong altitude.

### Backup job shape

Single scheduled workflow, daily overnight, plus `workflow_dispatch` for on-demand runs before anything
destructive:

```
pg_dump (full, gzipped)  →  upload artifact  →  restore into throwaway Postgres  →  assert row counts
```

The verification step is part of the same run, not a separate job — a dump that cannot be restored should
fail the run that produced it.

**Reuse, don't rebuild**: `pnpm pg:up` already stands up Postgres in Docker and applies every migration
in order `[from: package.json:15]`, and `test:pg` already runs against it. The restore drill uses the same
machinery rather than inventing a parallel path.

*(Written when `pg:up` ran Postgres 16 and the drill therefore could not reuse it. Since issue #26 the
compose file runs `postgres:17-alpine`, so the major now matches both production and the drill's own
container — but the drill still stands up its own bare container, because it must restore into an
**empty** database with no migrations applied.)*

### Messaging / Integration

Unchanged — synchronous only, no queue, no broker. The backup workflow is out-of-band from the application
entirely and shares no code path with it.

## Security

### New secret surface

**`DATABASE_URL` must be added as a GitHub Actions secret.** It currently lives only in Vercel environment
variables and the gitignored `.env.local`.

This is a deliberate expansion, recorded rather than assumed:

- Use a **read-only** Neon role for the dump if one can be created at no cost. A backup job has no reason
  to hold write credentials, and this is the cheapest available reduction in blast radius.
- The secret must never be echoed. `pg_dump` failures can print connection strings — redact or suppress
  verbose output.
- Artifacts contain a **full copy of the production database**.
  ~~Repository visibility is what protects them; the repo must stay private, and that is now a security
  property, not merely a preference.~~
  > ### ⚠️ CORRECTED 2026-08-12 — this is false now, and the exposure it describes actually happened
  >
  > **The repository is public** (`gh repo view` → `PUBLIC`, 2026-08-12). An Actions artifact is
  > downloadable by anyone with **read** access, which on a public repo is every logged-in GitHub user.
  > Roughly a week of the children's collection data was retrievable by anyone until 2026-08-10.
  >
  > *When it stopped being private is not established.* The interview record for this feature cites
  > `gh repo view` reporting **private** on 2026-08-05, so this line may well have been true the day it
  > was written. That does not soften it — it sharpens it. **A security property that depends on a
  > setting nobody watches is not a security property**, and this one silently stopped holding without a
  > single document noticing.
  >
  > It is also why the leak went unnoticed: the line states a protection confidently enough that a reader
  > checking "are the artifacts safe?" would stop here and be satisfied. The `$0/month` and "public repo"
  > constraints were carried faithfully elsewhere in the parent documents — they were simply never read
  > as statements about where the *backups* end up.
  >
  > **What actually protects them now is encryption, not visibility** (#40). The dump is GPG-encrypted to
  > a public key committed at `.github/backup-pubkey.asc` before upload, so the runner can write a backup
  > it cannot read. No decryption key exists in CI, and nothing whose compromise retroactively exposes
  > past dumps.
  >
  > **Making the repo private is not the fix and must not be treated as one.** It was tried first and
  > reverted: rulesets are unavailable on private repos on GitHub Free, so it disabled the branch
  > protection enforcing the CI gates — fixing an exposure by removing an enforcement mechanism.
  >
  > The residual risk moved rather than vanishing: **lose the private key and every dump in the 90-day
  > window is silently unrecoverable.** See `docs/RESTORE.md` §3.2 and #45.

### Unchanged

Every boundary in the parent document stands: the fail-closed `signIn` allowlist, the two-layer admin gate,
child profile selection as a cookie convenience rather than a security boundary, HMAC-signed offers, and no
secret in the client bundle. **This feature touches none of them.**

The V3 change is confined to a client component's confirmation UX. `removeProfileAction` keeps its
`withParent` gating exactly as-is — the guard is additive friction, not a replacement for authorization.

## Testing

### New test obligations

| What | Type | Why |
|------|------|-----|
| `resetPool()` leaves `collections` untouched | Unit or contract test | T7 — pins the split so it cannot be quietly re-merged |
| Production-host detection correctly classifies prod vs local `DATABASE_URL` | Unit test | The guard's whole value rests on this predicate being right; a false negative silently disables it |
| Restore-and-assert on every backup run | Automated drill in the workflow | T5 — satisfies Business Q4(A) mechanically rather than by discipline |

### Deferred — recorded, not silently dropped

The general property-based test *"no service path can delete a `collections` row it doesn't own"* is
**out of the first slice** (Business Q5). The parent Technical Environment makes Property-Based Testing a
**blocking** constraint, so this is a live tension, not a preference — tracked as **OQ-CS-3**.

Position taken: T7's narrow test closes the specific hole being fixed. Shipping slice 1 with a narrow test
is strictly better than shipping it with none, and materially better than deferring the whole slice until
the broad PBT exists. That reasoning should be re-examined, not inherited, when OQ-CS-3 is addressed.

### CI/CD Gates

**Notable interaction with parent OQ-T-2**: `.github/workflows/` does not exist today `[from: ls]`. This
feature creates it. The parent's declared-but-unenforced CI gates (`typecheck` → `test` → `build`, plus
`test:pg`) have been waiting on exactly this mechanism.

**Not scoped in here** — adding CI gates is a separate decision with its own trade-offs, and quietly
widening this feature to include them would be scope creep. But the marginal cost of a second workflow file
drops to near zero once the first exists, and that is worth knowing when OQ-T-2 is next considered.

## Implementation Notes

Facts the build stage will hit immediately. Not decisions.

- **`pg_dump` needs a standard `postgres://` connection string**, not the `@neondatabase/serverless` HTTP
  driver the app uses. Neon's `DATABASE_URL` is a standard connection string, so this should be a
  non-issue — but it is the first thing to verify.
- **Pin the `postgresql-client` major version** (≥ 16) explicitly in the workflow. Relying on the runner's
  default invites a silent break when the image drifts and `pg_dump` finds itself older than the server.
- **Neon may idle-suspend a free-tier database.** A nightly job hitting a cold instance should tolerate the
  wake-up latency rather than failing the run.
- **`workflow_dispatch`** is included as an assumption, not a confirmed answer (T3's sub-question went
  unanswered). Cheap to remove if unwanted.
